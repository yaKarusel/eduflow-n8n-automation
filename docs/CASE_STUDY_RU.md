# EduFlow — портфолио-кейс по n8n-автоматизации

> Production-style система для онлайн-школы: квалификация лидов из Instagram, обработка комментариев, контент-операции, ежедневная аналитика и централизованные ошибки.

[Вернуться к техническому README](../README.md) · [Сценарий пятиминутного демо](DEMO_SCRIPT.md) · [Архитектура](ARCHITECTURE.md)

## Задача бизнеса

Онлайн-школа теряет тёплые обращения, когда менеджеры вручную разбирают Direct и комментарии. Одновременно согласование контента происходит в чатах, отчёты собираются вручную, а повторная доставка webhook может отправить клиенту несколько одинаковых сообщений.

## Что я спроектировал

Систему из пяти workflow в n8n и отдельного бизнес-слоя в PostgreSQL:

1. Определение намерения пользователя, scoring и квалификация лида из DM.
2. Превращение комментариев с ключевыми словами в лиды и личные ответы.
3. Машина состояний контента: черновик → согласование → публикация → метрики.
4. Ежедневный Markdown/JSON-отчёт по воронке.
5. Единый обработчик ошибок с correlation ID и очисткой чувствительных данных.

## Почему это не просто «несколько нод»

- Дубликаты webhook блокируются транзакцией и уникальными ключами PostgreSQL.
- Состояние не хранится в памяти процесса и переживает перезапуск контейнеров.
- Все значения в SQL передаются параметрами `$1…$N`.
- Исходящие запросы имеют устойчивые idempotency keys и durable ledger.
- Mock API принудительно воспроизводит `429`, единичные и постоянные `500`.
- Acceptance suite проверяет итоговое состояние БД, а не только HTTP-код.
- Одинаковый workflow переключается между mock и live через окружение.
- Docker-окружение ограничено по памяти, PID и правам; логи и execution data ограничены.

## Проверенный результат

| Сценарий | Результат |
|---|---|
| Повторная доставка одного DM | Одна запись и один исходящий ответ |
| Комментарий с ключевым словом | Создан лид, отправлен один private reply |
| Первый ответ провайдера `429` | Автоматический retry, итог `SENT/200` |
| Постоянный `500` | Итог `FAILED/500`, создана очищенная ошибка |
| Одобренный контент | Статус `PUBLISHED`, сохранён publication ID |
| Ежедневная аналитика | Одна Markdown/JSON-запись на дату |

## Стек

`n8n 2.33` · `PostgreSQL 16` · `Docker Compose` · `Node.js mock API` · `Caddy` · `SQL migrations` · `GitHub Actions`

## Что этот кейс доказывает

- Я умею переводить бизнес-процесс в надёжную архитектуру автоматизации.
- Думаю о повторной доставке событий, гонках, retry и частичных отказах.
- Разделяю orchestration, бизнес-состояние и интеграционный слой.
- Умею делать воспроизводимое окружение, тесты, мониторинг, backup/restore и документацию.
- Не выдаю mock-интеграцию за подключённый клиентский Meta Business аккаунт.


## Честная граница live-режима

Репозиторий полностью демонстрирует архитектуру в безопасном mock-режиме. Для реального клиента дополнительно нужны его Meta Business assets, app review, актуальные permissions, проверка подписи webhook и процесс ротации токенов. Это отдельный этап клиентского onboarding, описанный в [LIVE_MODE.md](LIVE_MODE.md).
